# 1. 产品概述

## 1.1 产品定位

誓影 VowFrame 是一款本地运行的 AI 婚纱照生成工作台。

用户只需上传两张人物照片（每人一张），系统即可生成多种婚纱摄影风格的样片。用户选择满意的样片后，系统继续批量生成相同风格、不同姿势和构图的婚纱照片。

对于不满意的照片，用户可以单张或多选重新生成，并保留历史版本。

产品采用 **本地工作流 + AI 生图 API** 的模式。

## 1.2 核心理念

**先试拍，再批量；不满意可重生，生成结果不丢失。**

产品设计原则：

1. **操作简单**：用户不需要了解 Prompt、模型参数等技术概念。
2. **模型调用简单**：生图核心输入只有参考图和提示词。
3. **结果可控**：用户决定生成什么风格、生成多少张，以及哪些图片需要重新生成。
4. **任务可靠**：支持失败重试、取消、中断后恢复。
5. **历史可追溯**：重生不直接覆盖原图，支持历史版本恢复。
6. **本地持久化**：项目、原图、提示词、任务记录和生成结果都能持久保存。
7. **UI 精致**：整体体验接近高端婚纱摄影工作室，而非 AI 模型测试后台。

## 1.3 目标用户

- 希望低成本制作 AI 婚纱照的个人用户。
- 需要反复测试婚纱照风格和提示词的创作者。
- 需要批量生成双人写真图片的用户。

**首版实际用户：** 能自行启动本地服务、配置生图 API Key 的用户（开发者本人及懂技术的朋友）。

「用户不需要了解 Prompt、模型参数」指的是日常生成流程；一次性的安装与 API 配置仍由用户完成。面向完全不懂技术的用户（如托管 API、安装包）不在首版范围内。

## 1.4 首版范围

首版实现从照片上传到作品下载的完整闭环：

**创建项目 → 上传照片 → 生成风格样片 → 选择一种或多种满意风格，各拍一组 → 单张/多选重生 → 管理图片 → 下载作品**

同时具备本地项目管理、任务管理与异常恢复能力。

# 2. 核心业务流程

## 2.1 标准生成流程

### Step 1：创建项目

用户进入项目首页，点击「新建项目」。

系统创建一个本地项目，自动命名为「我的婚纱照」，支持修改名称。

进入照片上传步骤。

### Step 2：上传两张人物照片

上传区域包含：

- 人物 A 照片
- 人物 B 照片

每人只上传 1 张照片。不支持每人多张：同一人的多张照片在光线、角度、妆发上往往不一致，模型会把它们混合成「平均脸」，并且图片越多越容易把两个人弄混。

每张照片需标注角色：**新娘** 或 **新郎**。默认人物 A 为新娘、人物 B 为新郎，可一键互换。角色用于提示词中明确「哪张图是谁、穿什么」。

上传区给出照片建议：

- 近期照片，五官清晰，无遮挡（墨镜、口罩、大面积刘海）。
- 正脸或接近正脸，自然光。
- 半身照优于证件照；证件照可以使用，但效果可能较弱。

支持点击上传和拖拽上传。

上传后展示缩略图，支持替换和删除。

点击「开始生成风格样片」。

### Step 3：生成不同风格样片

系统内置 14 种预设风格（提示词见 [docs/prompts.md](prompts.md) 第 3 节）：

| 风格 | 风格说明 |
|---|---|
| 韩系极简 | 白纱黑西装、干净影棚、通透柔光 |
| 法式复古 | 复古礼服、巴黎街角、胶片色调 |
| 森系自然 | 草地、树林、林间阳光 |
| 海边日落 | 海岸、晚霞、黄金时刻 |
| 中式国风 | 秀禾服、传统中式庭院 |
| 高级光影 | 光影塑形、明暗对比、背景简洁 |
| 新中式 | 现代东方美学、月洞门、竹影、素雅 |
| 港风复古 | 90 年代港片色调、老街、霓虹 |
| 城市夜景 | 天台、城市灯火、虚化光斑 |
| 花海草原 | 花田、草原、开阔天空 |
| 冬日雪景 | 雪地、松林、冬日暖阳 |
| 欧式教堂 | 拱廊、彩窗、石柱、庄重浪漫 |
| 黑白经典 | 黑白影像、光影与情绪 |
| 生活日常 | 咖啡馆、书店、家中，自然纪实 |

每种风格生成 1 张样片，共 14 张。每种风格有 3～5 个场景变体，样片使用第一个；拍组时 AI 导演会按参考方式选择场景变体（见 3.3）。

每张样片独立创建生成任务，互不影响。

每种风格的样片占一个作品位置，重新生成样片会产生新版本，旧版本保留（与相册作品使用同一套版本机制，见 4.4）。

用户可以：

- 查看样片大图。
- 重新生成某一张样片。
- 选择某个风格继续。
- 重新生成全部风格样片。
- 返回上传步骤修改照片。

样片生成失败时，展示「重试」按钮，不影响其他成功样片。

### Step 4：选择风格拍组

一个项目可以拍多组风格，与真实婚纱摄影「影棚一套、外景一套、中式一套」的习惯一致。

每张样片卡片提供「用这个风格拍一组」，可以对任意多种风格使用，也可以对同一风格多拍几组。不存在「项目唯一选中的风格」：选一种风格不会让其他样片失效，试拍过的样片随时可以继续用来拍组。

每一组记录：

- 风格 ID。
- 作为风格依据的样片版本 ID（之后样片被重生，也能追溯这一组参考的是哪个版本）。
- 对应的风格提示词。

是否同时把样片图片作为参考图传给模型，见 3.3。

### Step 5：批量生成（拍一组）

点击「用这个风格拍一组」后，在弹窗中选择生成数量：

**4 / 8 / 12 / 20 张，默认 8 张。**

然后由 AI 导演写出本组的动作瞬间（见 3.3），用户预览、替换或修改后确认，才开始生成图片，并进入相册中该风格的分组。

每张照片使用一个不同的动作瞬间；同一风格再拍一组时，AI 导演会避开该风格已拍过的瞬间。

所有任务共享：

- 原始人物 A 照片。
- 原始人物 B 照片。
- 该风格的风格提示词。
- 该风格的样片（仅当采用「样片参考」方式时，见 3.3）。

每张任务分别使用自己的动作提示词。

点击开始前显示将创建的任务数量；如果配置了单价，同时显示预计费用（见 15.6）。

系统执行批量生成，实时展示每张图片的生成状态。

### Step 6：查看结果

生成成功的图片立即展示在婚纱相册中，无需等待全部任务完成。

用户可以：

- 查看图片大图。
- 单张重新生成。
- 换动作生成。
- 多选图片。
- 批量重新生成。
- 批量换动作。
- 查看历史版本。
- 下载单张或多张图片。
- 删除不需要的照片。

# 3. AI 生图设计

## 3.1 核心接口原则

所有生图任务统一使用同一个内部调用接口。

```python
generate_image(
    images=[...],
    prompt="..."
)
```

其中：

- `images`：一张或多张参考图片。
- `prompt`：文字提示词。

模型名称、鉴权、输出尺寸及其他供应商参数属于统一模型配置或适配层，不要求用户在每次生成时重复输入。

底层按照实际接入的生图服务 API 格式转换。

首版仅要求模型支持参考图 + 提示词生图；不开发独立身份模型或复杂生图流水线。

`images` 是**有序**列表，提示词通过「第一张图」「第二张图」引用参考图，因此顺序必须固定并随任务保存。

输出分辨率以所选模型的能力为准（通常为 1～2K）。首版不做图片放大。

具体使用哪个模型，以及下文标注「待验证」的决策，在第 0 阶段（见第 18 章）通过实际生成确定。

## 3.2 风格样片生成

输入：

```json
{
  "images": [
    "person_a.jpg",
    "person_b.jpg"
  ],
  "prompt": "第一张图是新娘，第二张图是新郎。保持两人的真实面貌，生成韩系极简风格婚纱照：新娘穿白色婚纱，新郎穿黑色西装，浅色影棚背景，柔和自然光，浪漫自然的双人合影。"
}
```

图片顺序与角色由用户的角色标注决定：新娘的照片始终放在第一张。

每种风格只需替换风格部分的提示词。

每种风格对应一个独立任务。

## 3.3 批量生成

批量生成有两种参考方式，**待第 0 阶段验证后选定一种作为默认**：

**方式 A：仅提示词**

```json
{
  "images": [
    "bride.jpg",
    "groom.jpg"
  ],
  "prompt": "第一张图是新娘，第二张图是新郎。保持两人的真实面貌，[风格提示词]，[动作提示词]，专业婚纱摄影效果。"
}
```

**方式 B：提示词 + 样片参考**

```json
{
  "images": [
    "bride.jpg",
    "groom.jpg",
    "selected_style.jpg"
  ],
  "prompt": "第一张图是新娘，第二张图是新郎，只参考这两张图的面貌。参考第三张图的摄影风格、服装和色调，但不参考第三张图中的人脸和构图。[动作提示词]，专业婚纱摄影效果。"
}
```

两种方式的取舍：

- 方式 B 的风格更统一，但样片中的人脸本身是模型的近似结果，模型可能参考它而偏离本人长相；也可能照搬样片构图，减弱动作变化。
- 方式 A 不存在上述问题，但每张图的风格细节（服装款式、场景）可能不完全一致。

两种方式只相差一张参考图，适配层无需区别对待。选定后在提示词管理中作为默认配置，不在用户界面暴露为选项。

### 动作瞬间由「AI 导演」编写

不再使用固定的动作库。每次拍组时，由一个文字模型（下称「AI 导演」）根据该风格的场景，一次写出本组需要的全部「动作瞬间」，用户预览、可替换或修改后，再开始生成图片。

为什么不用固定动作库：固定清单（原 12 个动作）无法照顾风格（海边、影棚、中式庭院用同一套动作），数量有限（拍 20 张必然重复、同风格第二组与第一组相同），景别分布也被清单写死。拍组的创意性比固定清单的可控性更重要。

AI 导演的职责边界：

- **只写「镜头」这一段**：机位与焦段、构图、人与场景的关系、光的落点，以及一个真实发生的瞬间（动作、互动、表情和视线）。画幅、人物锁定、服装与风格、画面质感、避免项仍是固定文字（见 [docs/prompts.md](prompts.md)），AI 导演无法改动。
- 为什么导演要写机位、构图和光，而不只是动作：构图没有人负责时，生图模型会默认画成居中、正面、平视、人物占满画面的合影；光不从场景光源出发时，人物像贴在背景上。2026-10-27 用真实照片对比验证过这两点（docs/prompts.md V3）。
- **只接收文字，不接收照片**：输入是风格名称、该风格的视觉语言和场景变体（不含服装）、张数、本风格已用过的瞬间标题。人物照片不会发给文字模型。
- **画幅也由导演决定**：每个镜头标为竖版或横版，以竖版为主，交代环境的远景（海平面、天际线、长廊）用横版。比例是构图的一部分；全局只有一个比例时，远景只能硬塞进竖版。具体比例由设置中的「画幅比例」决定，样片固定竖版，用户可在方案预览中逐张切换横竖。已生成作品的重新生成、加强长相、换景别沿用原比例。
- **场景变体的选择跟随拍组参考方式**：「只用两人照片」时导演可以为每个镜头选不同的场景变体，整组更有变化；「两人照片 + 样片」时只用样片所在的场景，因为样片会作为参考图，镜头换到别的场景会和参考图互相拉扯。
- 每个瞬间包含：简短标题（相册中显示的动作名称）、景别、描述文字。景别使用摄影的五级景别：远景（人物很小，环境为主）、全景（全身）、中景（膝盖或腰部以上）、近景（胸口以上）、特写（面部）。V3.4～V3.9 曾有不露脸的局部特写，已停用，旧作品上仍可显示。
  - 为什么不用影楼的「全身 / 七分身 / 半身 / 近景」：它只按「人露出多少」划分，缺了远景和特写这两头，导演每个镜头都被迫归进这四类。旧作品上的「七分身」「半身」仍照常显示。
  - 旧作品中的局部特写画面里没有人脸，不自动换脸，也不提供加强长相和换脸修正。
- 必须遵守的规则（写入导演提示词，并在后端校验）：
  - 景别由导演根据每个瞬间的动作和场景自由选择，整组要有节奏变化；后端**不校验景别数量分布**（构图属于创意决定，不用配额约束），用户可在方案预览中看到各景别张数并逐张切换。
  - 瞬间之间互不重复，也不与本风格已拍过的瞬间重复。
  - 动作、道具、头发不遮挡两人面部，两人面部清晰可见；不背对镜头、不剪影。不要求每张都有人看向镜头。
  - **不描述任何五官或长相**（例如眼型、脸型、鼻型）：长相只由参考照片决定。
  - 与该风格的场景一致（海边可以踏浪奔跑，中式庭院可以撑伞跨门槛）。
- 后端校验不通过时，自动请 AI 导演重写一次；仍不通过则明确报错，不静默降级为固定动作。

流程：

```text
「用这个风格拍一组」→ 选张数与图片模型 → AI 导演写出 N 个瞬间（文字，几秒，费用很低）
→ 用户预览：可对单个瞬间「换一个」或直接修改文字 → 确认后才创建付费的图片生成任务
```

导演方案在确认前不产生图片费用；确认后每个瞬间对应一个生成任务，瞬间文字写入任务的提示词快照，因此「重新生成」可以完全复现。

AI 导演使用的文字模型在设置中配置（`director_model`），与图片模型共用 88API 的 API Key。未配置时拍组不可用，并提示用户去设置。

已拍过的旧作品仍保留原来的固定动作（`pose_id`），不受影响。

## 3.4 提示词组合规则

> 提示词的具体文字与五段结构以 [docs/prompts.md](prompts.md) 为准；本节保留设计思路。

批量生成的提示词由三部分组合：

```text
人物保持提示（含图片与角色对应）
+
风格提示
+
当前动作提示
```

例如：

```text
人物保持：
第一张图是新娘，第二张图是新郎。保持两人的真实面貌及主要五官特征。

风格：
韩系极简风格，新娘穿白色婚纱，新郎穿黑色西装，浅色影棚背景，柔和自然光。
```

# 4. 重新生成机制

## 4.1 单张重新生成

图片卡片提供「重新生成」。

默认行为：

- 保持原参考图片。
- 保持原提示词。
- 创建一个新的生成任务。
- 成功后生成新版本。

原始图片保留。

需注意，相同参考图和提示词不能保证生成完全相同的姿势构图，但可以尽量保持相同的设计方向。

## 4.2 换动作

图片卡片提供「换动作」。

系统保持：

- 两张人物照片。
- 原风格样片。
- 风格提示词。

系统更换：

- 动作提示词。
- 必要的构图描述。

由 AI 导演为这张照片写一个新的动作瞬间：与当前瞬间不同，并避开同一风格中已有的瞬间。景别不限定，由 AI 导演根据风格决定。

换动作也是一次新的生成任务，并产生新的历史版本。

## 4.2.1 换景别

图片卡片和大图查看器提供「换景别」：远景 / 全景 / 中景 / 近景 / 特写（当前景别不可选）。

用途：喜欢某张照片的动作，但想要另一种景别，例如「以这张为基础生成全身照」。

系统保持：两张人物照片、风格提示词、这张照片的动作与互动。

系统更换：由 AI 导演把当前瞬间改写为目标景别（保持动作、互动和视线，只调整景别和相应描述）。

不把这张已生成的照片作为参考图传给模型：生成图里的人脸本身是模型的近似结果，以它为参考会让新图离本人更远（与 3.3 中「样片参考」的风险相同）。

换景别同样是新的生成任务，产生新的历史版本，原版本保留。支持多选批量换景别。

导演方案预览时，每个瞬间也提供同样的景别切换：切换后由 AI 导演按新景别改写该瞬间，不产生图片费用。

## 4.3 多选重新生成

相册支持多选图片。

用户勾选后出现底部批量操作栏。

支持：

**批量重生**

对每张选中图片复用其原参考图和提示词，分别创建新任务。

**批量换动作**

对每张选中图片保持人物和风格参考，分别替换动作提示词。

每张图片独立执行，成功或失败互不影响。

## 4.4 历史版本

每个作品位置（包括风格样片）维护自己的版本记录：

```text
作品 03
├── V1 原图
├── V2 第一次重生
├── V3 换动作版本
└── V4 第二次重生
```

版本功能：

- 默认展示当前版本。
- 支持查看所有成功生成的历史版本。
- 支持恢复旧版本为当前版本。
- 支持下载任意版本。

**新版本成功前，绝不覆盖原版本。**

如果重新生成失败，当前版本保持不变。

删除整个作品或历史版本必须有明确的用户操作，不因为重新生成自动删除旧图。

## 4.5 换脸修正

生图模型每次都会重新画脸，长相难免偏离。换脸修正在**最后一步**用本地 FaceFusion，把用户上传的原照身份换到当前版本的两张脸上：新娘原照换到画面中的女性脸，新郎原照换到男性脸。构图、服装、光线、动作完全不变。

- **默认自动执行**（2026-10-27 起）：每张样片和相册照片生成成功后，自动排一次换脸，换脸结果成为当前版本。设置页可关闭「生成后自动换脸」。手动入口仍保留：相册作品、风格样片的 ⋯ 菜单与图片查看器提供「换脸修正」，相册多选栏提供「批量换脸修正」。
  - 首版曾不自动执行，原因是侧脸、遮挡等情况尚未充分验证，换坏的结果会直接成为当前版本。改为自动后这个风险仍在，靠以下三点兜住：生图原图始终保留在历史版本中；照片上显示「换脸修正 · 对比」，可随时与原图对比；不满意可在历史版本中恢复原图，或关闭自动换脸。
  - 换脸**失败**时（例如找不到某人的脸），生图原图保持为当前版本，照片上显示失败原因。
  - 自动换脸的任务加入同一个批次，所以一个批次要等换脸也完成才算完成；批次的任务数会比照片数多（每张照片一个生图任务加一个换脸任务）。
  - 未配置 FaceFusion 时自动换脸不生效，不会排出注定失败的任务。
  - 旧作品中的局部特写（画面里没有人脸）不自动换脸。
- **结果是新版本**：成功后新增版本并设为当前版本，记录它来自哪个版本（来源版本）；原版本保留，可在历史版本中恢复。
- **总是从生图原图开始**：当前版本本身是换脸结果时，以它的来源版本为输入，不在换过的脸上再换一次。
- **其他操作也从生图原图出发**：对换脸版本做重新生成、加强长相、换动作、换景别时，读取的是它来源的生图任务（提示词、动作、景别、画幅），因为换脸任务本身没有提示词。
- **使用项目当前的人物照片**。
- **本地运行、不产生费用**：不弹出模型与费用确认，点击即开始。失败可重试，没有重复扣费的顾虑。
- **固定参数**：新娘 pass 使用模型 `hyperswap_1a_256`，新郎 pass 使用模型 `hyperswap_1c_256`，像素提升 `512x512`，强度 `0.5`（模型与像素提升由用户在 2026-10-27 用真实照片对比后选定；强度同日由 1.0 改为 0.5：1.0 会把参考照片里证件照式的中性表情一起换上去，笑容被抹掉，0.5 在接近本人与保留生成画面的表情、光线之间折中）。参数记录在任务的配置快照中。
- **不能假装成功**：FaceFusion 在找不到指定性别的脸时会原样输出并报告成功。因此换脸前必须先检测：
  - 新娘原照须识别为女性、新郎原照须识别为男性，否则失败并提示「新娘和新郎的照片可能放反了，请在工作台点『交换』后重试」。
  - 当前版本中须能找到至少一张女性脸和一张男性脸，否则失败并说明缺少谁的脸（例如侧脸角度过大或被遮挡）。
- **单独排队**：换脸任务一次只运行一个（显存有限），不占用生图的并发名额，也不受生图限流影响。
- **FaceFusion 不可用时**（未配置或安装目录不完整），换脸按钮置灰并说明原因；设置页显示 FaceFusion 状态。

## 4.6 对比

对比服务于一个决定：留哪个版本，或留哪几张照片。因此对比窗口内可以直接「设为当前」「下载」。

**两种方式，按构图是否相同选择：**

| | 切换 | 并排 |
|---|---|---|
| 适用 | 构图完全相同，只有脸不同（换脸版本与其来源版本） | 构图不同（重生、换动作、换景别的版本，不同照片，不同风格样片） |
| 操作 | 同一位置显示一张，按住空格或按住按钮显示另一张，松开切回 | 2～4 张大图并排 |
| 放大 | 两张同步放大、同步拖动 | 各自放大 |

- 不用左右拖动的分割滑块：分割线会穿过脸，比较的是 A 的左眼和 B 的右眼；切换才是同一位置看同一部位。
- 两张构图相同的版本默认切换，其余默认并排；用户可手动改变方式。
- **原照栏**：对比窗口固定显示新娘、新郎原照（可收起）。判断像不像要和原照比，不是和另一张生成图比。
- **不显示相似度分数**：实测中分数提高时肉眼仍感觉没区别，分数会误导选择（见 V1.1 变更摘要「不设相似度或审美打分」）。
- 一次最多 4 张。

**入口：**

| 入口 | 对比内容 | 默认方式 |
|---|---|---|
| 当前版本为换脸结果时，照片上的「对比原图」 | 换脸版本与来源版本 | 切换 |
| 历史版本中勾选两个版本 | 同一位置的两个版本 | 构图相同则切换，否则并排 |
| 相册多选 2～4 张后「对比所选」 | 不同作品的当前版本 | 并排 |
| 工作台样片多选 2～4 张后「对比所选」 | 不同风格样片的当前版本 | 并排 |

首版不做脸部自动放大并排（需要为每张图检测人脸位置），手动放大即可。

# 6. 任务系统

## 6.1 设计目标

所有生成请求都必须作为独立任务管理。

无论是：

- 风格样片生成。
- 批量生成。
- 单张重新生成。
- 多选重新生成。
- 换动作。

都使用同一套任务系统。

### 核心原则

**先保存任务，再执行请求；先保存图片，再标记成功。**

不能只把生成任务保存在浏览器内存里。

## 6.2 单张任务状态

| 状态 | 含义 |
|---|---|
| `waiting` | 等待执行，调度器会自动启动 |
| `held` | 已搁置：尚未发出请求，需用户点击「继续」才会执行 |
| `running` | 正在调用模型 |
| `completed` | 已成功生成并保存 |
| `failed` | 明确失败 |
| `cancelled` | 已取消 |
| `interrupted` | 已中断：请求可能已经发出（可能已扣费），但结果无法确认 |

每张任务独立记录状态。

`held` 用于所有「系统不能自作主张继续花钱」的场景，统一一种处理方式：

- 后端重启时，遗留的 `waiting` 任务转为 `held`。
- 鉴权失败、余额不足、存储空间不足时，同批其余 `waiting` 任务转为 `held`。

用户点击「继续」后，`held` 任务转回 `waiting`。

额外记录：

- 创建时间。
- 开始时间。
- 结束时间。
- 错误信息。
- 自动重试次数。
- 所属批次。
- 使用的参考图（有序）。
- 风格 ID、动作 ID。
- 最终提示词。
- 模型配置快照。
- 生图服务任务 ID（如有）。
- 输出文件路径。

## 6.3 批次状态

批次可以包含多个单张任务。

批次状态**不单独存储**，每次读取时由其下任务的状态汇总得出：

| 批次状态 | 判断条件 |
|---|---|
| 进行中 | 存在 `waiting` 或 `running` 任务 |
| 已搁置 | 不存在进行中的任务，但存在 `held` 任务 |
| 需处理 | 全部结束，但存在 `failed` 或 `interrupted` 任务 |
| 已完成 | 全部结束，且没有需处理的任务 |

这样不会出现「批次显示完成，但任务还在跑」之类的不一致。

一个批次失败，不等于全部图片失败。

例如：

```text
批次 #1001

总数：8
已完成：5
生成中：1
等待中：1
失败：1
```

已完成的图片立刻保存和展示。

## 6.4 生成任务调度

本地后端负责执行任务。

默认并发数量为 2。

执行规则：

1. 创建所有任务记录（状态 `waiting`）。
2. 调度器从数据库读取 `waiting` 任务。
3. 按并发限制启动任务。
4. 成功后保存文件和状态。
5. 失败时记录原因。
6. 继续处理其他可执行任务。
7. 更新前端进度。

任务应由持久化数据库驱动，不能只存在于内存队列。

前端通过轮询或实时事件获取进度。

# 7. 取消、继续与恢复

首版不提供用户手动「暂停」。一批最多 20 张、并发 2，整批通常几分钟内完成；「暂停」与「取消剩余」对用户的区别很小，却会让状态组合成倍增加。需要停下来时，用户使用「取消剩余」，之后可随时发起新的生成。

## 7.1 取消剩余任务

点击「取消剩余」。

弹出确认提示：

「将保留已完成的照片，尚未开始的任务将被取消。」

执行：

- `waiting` 和 `held` 任务转为 `cancelled`。
- 不删除已完成图片。
- 正在执行的请求允许完成，结果正常保存。

如果模型服务支持取消已提交的请求，适配层可尝试取消；否则界面说明：已提交的请求会继续完成并产生费用。

## 7.2 继续剩余任务

当批次处于「已搁置」状态（见 6.2、6.3）时，显示「继续剩余」。

行为：

- `held` 任务转回 `waiting`，由调度器继续执行。
- 不重复执行已完成任务。
- `failed` 和 `interrupted` 任务不会被自动重试，需用户单独处理。

## 7.3 取消单个等待任务

任务中心中可取消某一个 `waiting` 或 `held` 任务。

## 7.4 浏览器关闭

当用户关闭浏览器时：

- 只要本地后端继续运行，任务就继续执行。
- 图片和任务状态持续保存在本地。
- 再次打开网页，自动加载实际任务进度。

用户不需要保持工作台页面打开。

## 7.5 本地服务关闭或电脑重启

系统重启后读取 SQLite 任务记录。

根据任务类型处理：

**已完成任务**

恢复图片展示。

**等待任务**

转为 `held`，等待用户点击「继续剩余」。

**正在执行但已中断的任务**

如果适配器支持查询远程任务（见 7.6），先查询并按结果处理。

否则标记为 `interrupted`，由用户决定重试或放弃。

**明确失败任务**

显示失败原因及重试操作。

重启后不自动重新提交可能产生费用的生成任务。

## 7.6 远程任务恢复限制

如果 AI 服务支持：

- 异步任务 ID。
- 任务状态查询。
- 结果重新获取。

则系统应优先利用这些能力恢复任务。

是否需要实现这部分，取决于第 0 阶段确定的模型：如果选定的服务只提供同步接口，则不实现远程查询，中断任务直接标记为 `interrupted`。

同步请求在本地服务关闭时无法接续，系统不声称任务能够原地续跑。

界面提示：

「上次请求的结果无法确认，你可以重新发起生成。重新请求可能产生额外费用。」

# 8. 错误与异常处理

## 8.1 生图失败

任务失败时：

- 显示失败状态。
- 保留原参考图和提示词。
- 支持单独重试。
- 不影响其他任务。

## 8.2 网络错误

如果请求确定尚未发出（例如连接建立失败）：

- 自动重试，最多 2 次，计入自动重试次数。
- 超出后标记为 `failed`。

如果请求可能已被服务端接收但无法确认结果（例如读取响应超时）：

- 有服务商任务 ID 且支持查询时，先查询。
- 否则标记为 `interrupted`。
- 不自动重复提交。

## 8.3 API 限流

发生限流时：

- 根据 API 返回的等待建议进行退避。
- 临时停止启动新任务。
- 不进行高频重复请求。
- 持续限流时提示用户。

## 8.4 API 余额不足或鉴权失败

- 同批其余 `waiting` 任务转为 `held`。
- 告知用户检查模型设置或账户余额。
- 用户修复后点击「继续剩余」。

## 8.5 生成中切换页面

不影响任务执行。

可以进入其他项目，也可以浏览已经生成的图片。

## 8.6 重复点击

开始生成后按钮立即进入已提交状态。

后端同时提供重复提交保护，避免短时间重复请求产生重复任务和费用。

## 8.7 存储空间不足

检测到文件无法保存时：

- 其余 `waiting` 任务转为 `held`。
- 显示存储空间不足，并展示本地数据目录位置。
- 保留数据库记录。

如果模型已经生成结果，但文件无法成功保存，不能错误标记为 `completed`。

## 8.8 文件缺失或损坏

如果数据库存在记录，但图片文件不存在：

- 展示文件缺失状态。
- 保留历史记录。
- 允许删除无效记录或重新生成。

不自动静默删除用户记录。

## 8.9 重生失败

原来的成功版本继续展示。

新版本任务失败不会覆盖或删除旧版本。

## 8.10 修改参考图或提示词

每个任务在创建时记录当时使用的参考图版本、提示词和模型配置。

用户之后修改项目设置，不应改变已经创建的任务内容。

原参考图不因用户上传新照片而被立即删除，只要仍有历史任务引用，就必须继续保留。

## 10.1 本地目录

建议采用：

```text
vowframe/
├── frontend/
├── backend/
│   ├── main.py
│   ├── generator.py
│   ├── task_manager.py

```

图片文件由本地文件系统保存。

SQLite 负责保存：

- 项目。
- 图片引用。
- 风格。
- 提示词。
- 任务。
- 版本关系。
- 操作状态。

## 10.2 文件保存规则

每次生成结果都使用独立文件名。

禁止直接覆盖旧版本。

生成结果需要：

1. 写入临时文件。
2. 确认写入成功。
3. 原子性地移动到正式文件位置。
4. 更新数据库记录为完成。

尽量避免出现数据库显示成功但正式图片尚未保存的情况。

## 10.3 数据删除

首版只提供用户明确发起的删除。存储统计、临时文件清理、任务记录清理属于 P1。

后端启动时自动删除 `temp/` 目录中的残留文件：这些文件在任务标记完成前就会被移走，残留文件一定没有被引用。

### 删除作品

支持单张或多选删除。

删除前需要提示，如果该作品包含多个历史版本，应明确删除范围。

### 删除项目

删除项目前：

- 提示此操作会删除照片、历史版本及任务记录。
- 处理当前项目仍在运行的任务。
- 需要二次确认。

项目存在 `running` 任务时，先取消剩余任务，等运行中的请求结束后再删除，避免删除后产生孤立结果。

# 11. 数据结构

首版主要使用以下数据实体。

## 11.1 Project

```text
id
name
status
person_a_image_id
person_a_role          # bride | groom；人物 B 永远是相反角色，不单独存储
person_b_image_id

```

用于保存项目基础信息与当前选择。

项目不保存「选中的风格」：一个项目可以拍多组风格，每组的风格记录在拍组批次（GenerationBatch.style_id、reference_preview_version_id）和作品位置（PhotoSlot.style_id）上。

## 11.2 ImageAsset

```text
id
project_id
file_path
asset_type
created_at
```

用于管理本地图片文件。

`asset_type` 包含原图、样片、作品及其他必要类型。

## 11.3 StylePreset

```text
id
name
description
prompt_template
is_builtin
```

用于保存预设婚纱风格。

## 11.4 PhotoSlot

```text
id
project_id
batch_id
kind                   # preview | photo
style_id
current_version_id
created_at
```

代表一个作品位置：风格样片（`preview`）或相册作品（`photo`）。

例如第 3 张婚纱照无论重生多少次，都属于同一个 `PhotoSlot`。韩系极简的样片无论重生多少次，也属于同一个 `PhotoSlot`。

## 11.5 PhotoVersion

```text
id
photo_slot_id
image_asset_id
generation_task_id
version_number
created_at
```

用于保存作品历史版本。

用户恢复旧版本时，更新 `PhotoSlot.current_version_id`，不需要复制或覆盖图片文件。

## 11.6 GenerationBatch

```text
id
project_id
batch_type
style_id                       # 拍组批次的风格；样片批次为空

client_request_id              # 防重复提交
created_at
```

不存储批次状态和总数，由所属任务汇总计算（见 6.3）。

批次类型：

- 风格样片批次。
- 正式婚纱照批次。
- 重生批次。

## 11.7 GenerationTask

```text
id
project_id
batch_id
target_slot_id
status
reference_image_ids    # 有序 JSON 数组
style_id
pose_id                # 旧版固定动作；新任务为空
moment_title           # AI 导演写的瞬间标题；样片为空
moment_shot_size       # wide | full | medium | close | extreme_close（旧作品可能为 detail | three_quarter | half）；样片为空
regenerate_mode        # same | identity_boost | change_pose | change_shot；首次生成为空
prompt                 # 最终组合后的完整提示词
model_config_snapshot
provider_task_id
output_asset_id
error_code
error_message
auto_retry_count
retry_of_task_id       # 用户手动重试时指向原任务
created_at
started_at
finished_at
```

每条任务都保存完整的生成上下文。

重试语义：

- **自动重试**（请求确定未发出时，见 8.2）：在同一条任务上进行，`auto_retry_count` 加一。
- **用户手动重试**（`failed` / `interrupted`）：复制原任务的上下文，新建一条任务，`retry_of_task_id` 指向原任务。原任务记录保持不变。

```text
used_by_batch_id       # 确认拍摄后指向创建的批次；未使用为空
created_at
updated_at
```

拍组前的「导演方案」。确认拍摄后不可再修改，只能用一次。

```text
api_key_reference
default_image_ratio
max_concurrency
```

**Python + FastAPI**

负责：

- 生成任务调度。
- AI 模型调用。
- 历史版本管理。
- 异常恢复。
- 下载与删除。

**SQLite**

无需额外安装数据库服务。

使用后端本地任务执行器。

初期不需要：

- Redis。
- Celery。
- Kubernetes。
- 分布式任务系统。

## 13.5 AI 模型适配层

统一接口：

```python
generate_image(images, prompt)
```

针对具体服务商编写适配器。

模型适配器负责：

- 调用生图 API。
- 传输参考图。
- 处理同步或异步响应。
- 获取图片结果。
- 报告可识别的错误。
- 查询远程任务状态（如支持）。
- 取消远程任务（如支持）。

具体使用哪家模型服务，在第 0 阶段决定。首版只需实现选定服务的一个适配器。

### 13.5.1 文字模型适配（AI 导演）

```python
write_moments(style, scene_prompt, count, avoid_titles) -> list[Moment]
```

- 通过 88API 的 `/v1/chat/completions` 调用 `director_model`，要求返回 JSON。
- 同步调用，超时 60 秒；失败按普通错误提示，不影响已有任务。
- 模拟模式下使用固定的示例瞬间，开发与测试不产生费用。

前端与后端都运行在本地。

```text
http://localhost:5173
```

访问。

正式本地运行模式可以由 FastAPI 同时托管构建后的前端静态资源，提供统一的本地访问入口。

默认仅监听本机回环地址，避免意外向局域网或公网开放接口。

# 14. 隐私与安全

## 14.1 照片隐私

原始照片和生成结果默认保存在本地。

使用云端生图服务时，必须将所需参考照片发送给服务商。

首次配置或首次使用云端生成时，提示用户这一事实。

用户应确认有权使用上传人物的照片。

## 14.2 API Key

- 不在浏览器前端保存明文 API Key。
- 不将 API Key 写入生成任务记录。
- 不在日志中输出 API Key。
- 使用受保护的本地后端凭据存储方式。
- 设置页支持更新和清除凭据。

## 14.3 本地安全

- 后端默认仅允许本机访问。
- 文件接口不能随意访问应用数据目录以外的路径。
- 删除操作需要确认。
- 删除文件前检查引用关系（如仍被任务引用的参考图不可删除）。
- 敏感照片不主动上传到无关服务。

- 当前项目。
- 当前工作阶段。
- 已生成图片。
- 正在运行的任务。

## 15.2 切换项目

允许不同项目存在未完成任务。

切换页面或项目不自动取消任务。

任务中心能够查看所有项目的运行情况。

## 15.3 修改原照片

如果用户替换人物照片：

- 后续新创建的任务使用新照片。
- 已创建任务继续使用其原始参考图快照。
- 已生成的历史结果保持不变。
- 用旧照片生成的样片和作品标记为「旧照片生成」，并提示「照片已更换，建议重新生成风格样片」。不删除、不隐藏任何已有内容。原因：旧样片是用旧照片生成的，用它拍组可能让新旧长相互相冲突，但它仍有比较价值，删不删由用户决定。

## 15.5 提示词查看

图片详情提供可折叠的「生成信息」。

内容包括：

- 使用的风格。
- 动作名称。
- 提示词。
- 所属任务。
- 生成时间。
- 模型名称。

支持复制提示词。

## 15.6 批量操作确认

批量重生需要显示即将新增的任务数量。

例如：

「将为选中的 5 张作品分别生成一个新版本，共创建 5 个生成任务。」

如果设置中配置了单价，追加预计费用：

「预计费用约 ¥2.50（按单价 ¥0.50 / 张估算）。」

所有会创建生成任务的操作（样片、批量、重生、换动作）都遵循此规则，避免用户误以为这是免费、无成本的本地操作。

## 15.7 生成中退出

关闭浏览器时不拦截退出，后端继续运行。

如果用户明确点击「退出并停止本地服务」，应先提示存在尚未完成的任务。

## 15.8 空状态

使用一个统一的空状态组件（图标 + 一句说明 + 可选的操作按钮），覆盖以下情况：

- 暂无项目。
- 尚未上传照片。
- 风格样片正在生成。
- 样片全部失败。
- 尚未选择风格。
- 相册没有照片。
- 任务中心没有任务。
- 网络或模型服务不可用。

每种情况只需提供文案和按钮，不单独设计页面。不展示空白屏幕或不明确的错误占位。

# 17. 核心验收标准

## 17.1 标准流程

**测试场景：**

用户创建项目并上传两张照片。

**预期结果：**

可以生成 6 张不同风格样片，选择其中一个风格后批量生成 8 张不同动作婚纱照。

所有成功图片都可在相册查看和下载。

## 17.2 单张重生

**测试场景：**

用户对第 3 张执行重新生成。

**预期结果：**

创建新的生成任务，成功后新增 V2，原 V1 保留，支持恢复。

## 17.3 多选重生

**测试场景：**

用户选择第 2、4、7 张重新生成。

**预期结果：**

创建 3 个独立任务。成功图片更新版本，失败图片继续显示原版本。

## 17.4 部分失败

**测试场景：**

8 张任务中 5 张成功、2 张失败、1 张等待。

**预期结果：**

5 张成功图片正常保存；可以单独重试失败任务，等待任务继续执行，不需要重新生成全部图片。

## 17.5 浏览器关闭

**测试场景：**

生成过程中关闭浏览器，再重新打开。

**预期结果：**

后端未停止时，任务继续运行；重新打开后显示真实任务状态和已完成图片。

## 17.6 服务重启

**测试场景：**

任务执行中关闭后端并重新启动。

**预期结果：**

已完成图片保留；等待任务变为「已搁置」，点击「继续剩余」后继续执行；无法确认结果的请求标记为「已中断」，不会被自动重复提交。

## 17.7 重生失败

**测试场景：**

新生成版本失败。

**预期结果：**

旧版本仍然可查看、下载和恢复，不会消失。

## 17.8 角色对应

**测试场景：**

用户上传两张照片，把人物 A 标注为新郎、人物 B 标注为新娘，生成样片。

**预期结果：**

请求中新娘的照片排在第一张，提示词中的角色描述与之对应。

## 17.9 替换照片

**测试场景：**

用户已用某风格拍过一组后，替换人物 A 的照片。

**预期结果：**

已有样片与作品标记为「旧照片生成」并提示重新生成样片；所有已生成的样片、作品与历史版本都保留。

## 17.10 重复提交

**测试场景：**

用户连续快速点击开始生成。

**预期结果：**

同一次用户操作不会创建重复批次。

## 17.11 下载与删除

**测试场景：**

用户批量下载部分图片，然后删除一个不需要的作品。

**预期结果：**

下载文件可正常打开；删除只影响指定作品及其明确确认的范围，不影响其他作品。

## 17.12 用户界面

**测试场景：**

用户在正常流程中操作产品。

**预期结果：**

无需手动输入提示词即可完成上传、选风格、批量生成、重生和下载。

所有核心操作有明确反馈，不出现长期无响应、错误状态不明或结果无故消失的情况。

# 18. 推荐开发顺序

原则：**先验证模型，再搭系统。** 模型的实际表现（能否保持长相、耗时、同步还是异步、失败方式）会反过来决定界面和任务系统需要多复杂，因此必须最先确认。

## 第 0 阶段：模型验证（脚本，约 1～2 天）

不写界面，只用脚本调用候选模型，把结果按组存入文件夹，由用户直接看图判断。**不做相似度或审美打分。**

需要回答的问题：

| 问题 | 对比方式 |
|---|---|
| 选用哪个模型 | 2～3 个候选模型，相同输入各生成若干张 |
| 用什么照片 | 证件照 / 半身生活照 / 两人合影 |
| 批量参考方式 | 方式 A（仅提示词）/ 方式 B（带样片参考），见 3.3 |
| 角色是否对应正确 | 检查新娘、新郎的服装和长相是否搞反 |

同时记录客观信息：

| 记录 | 决定什么 |
|---|---|
| 单张耗时 | 任务进度展示方式、并发默认值 |
| 单张价格 | 默认单价、费用提示 |
| 失败率与报错类型 | 错误分类与重试规则 |
| 同步还是异步接口 | 是否实现远程任务查询（7.6） |
| 支持的参考图数量、比例、分辨率 | 适配层参数 |

产出：选定模型、默认参考方式、经过实测的风格与动作提示词初稿。

## 第一阶段：最小可用闭环（真实模型）

完成：

- 项目创建与持久化（SQLite + 本地文件）。
- 上传照片与角色标注。
- 生图适配器（仅选定的一家服务）。
- 各内置风格的样片生成、样片重生。
- 选定风格、批量生成。
- 单张重生与历史版本、恢复。
- 单张下载。
- 任务入库、先保存图片再标记完成、重启后不自动重新提交。

界面先使用基础样式，保证流程可用。

## 第二阶段：完整功能

完成：

- 换动作（单张及批量）。
- 多选模式与批量重生。
- 任务中心：取消剩余、继续剩余、重试。
- `held` / `interrupted` 状态处理与项目进入时的恢复提示。
- 错误分类与限流退避。
- 重复提交保护。
- 批量 ZIP 下载。
- 作品删除、项目删除。
- 任务数与费用提示。

## 第三阶段：体验打磨

完成：

- 按第 5 章视觉规范完善 UI。
- 统一空状态组件。
- 图片查看器细节（上一张 / 下一张、保留滚动位置）。
- 生成信息展示。
- 断点恢复等异常场景的完整验证。

# 19. 首版完成标准

当以下业务链路可以完整、稳定地执行时，视为 V1.0 达到可用状态：

**用户创建项目，上传两张人物照片并标注角色，生成不同风格样片，为一种或多种满意的风格各拍一组不同姿势的婚纱照。**

生成过程中可以关闭浏览器、切换项目或取消剩余任务；重新打开后能够找到已生成图片，恢复可继续的任务。

批量生成部分失败时，用户可以只处理失败的图片。

对不满意的作品，可以单张或多选重新生成，也可以换动作。所有成功的历史版本都能查看和恢复。

用户可以下载满意作品，删除不需要的作品，并且不会因为正常的重新生成、失败、刷新或中断操作而丢失已完成照片。

# 20. 最终产品定义

**产品名称：誓影 VowFrame**

**产品形态：本地 AI 婚纱照工作台**

**核心生图能力：参考图 + 提示词**

**核心业务闭环：**

上传双人照片 → 风格样片 → 按风格拍组（可多组） → 单张/多选重生 → 历史版本 → 下载作品。

**核心可靠性能力：**

持久化任务 → 独立执行 → 失败重试 → 取消与继续 → 重启恢复 → 不重复扣费。

**核心设计目标：**

让用户像使用一间数字婚纱摄影工作室一样，轻松选择风格、批量拍摄、反复挑选，直到获得满意的照片。

不追求首版功能庞杂，重点做到：

**界面精致、操作直观、生成灵活、任务可靠、结果不丢。**
